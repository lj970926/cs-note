# AI 代码 Review 策略

> [!abstract] 一句话
> 「review 不过来」通常不是速度问题，而是**流程设计问题**：把人眼当成唯一的信任来源，就会让系统里最慢、最容易疲劳的一环成为瓶颈，于是 AI 越快你越崩溃。
> 解法是分层——**机器能判的归机器，独立 agent 能审的归 agent，能在计划阶段拦的归计划，只把最高危的一小部分留给人眼。**

## 问题：产出速率 > 审查带宽

[[Cursor Agent Best Practice]] 里有一句几乎就是为这个场景写的：

> agent 工作得越快，你的 review 流程就越重要。

注意是"**流程**越重要"，不是"你要读得越快"。人眼带宽基本恒定，靠加班读 diff 是线性扩展，而 agent 的产出是并行扩展——**用线性去追并行，必然崩**。

所以真正要改的是信任来源的结构，而不是阅读速度。

---

## 一、先把「必须人读」的量压下去

### 1.1 用可验证信号替代人眼

> agent 无法修复它"看不见"的问题。使用强类型语言，配置 linters，并编写测试。给 agent 明确的信号，以判断更改是否正确。 —— [[Cursor Agent Best Practice]]

能自动判定的就别用人判定。类型检查、linter、CI、测试跑一遍是秒级，人读一遍是小时级。把有限的 review 预算留给**机器判不了的东西**。

这条还有个反向推论，很有用：

> [!warning] 不可验证 = 不可 review
> 如果一个改动没有任何可验证信号（无测试、动态类型、无 lint、无 CI），那它本质上**无法被 review**。此时正确的动作不是"更努力地读"，而是**先补测试再谈合并**。

### 1.2 分级，别一刀切

| 档位 | 典型改动 | 策略 |
| --- | --- | --- |
| 机械改动 | 格式化、重命名、依赖升级、批量适配 API | 信任工具与 CI，只看 diff 统计 |
| 一般逻辑 | 业务函数、参数调整、新增分支 | 读 diff + 跑测试 |
| 高危区 | 并发/锁、内存生命周期、错误处理、权限、序列化边界 | 必须逐行读，不接受"看起来对" |

**高危区的判定标准很简单：这里的 bug 不会让测试变红，只会让线上偶发挂掉。**

这类代码恰恰是 AI 最容易"看起来很对"的地方，也正是 [[大型项目源码阅读方法论]] 里强调的那种需要理解上下文才能判断正确性的部分——省不了。

## 二、用独立 agent 审查 agent

人眼带宽有限，但 agent 带宽便宜。[[Subagent 的好处与适用边界]] 提供了两个直接可用的机制。

### 2.1 角色与模型异构

> 每个子任务可以用不同的 system prompt（审查者、研究员、测试编写者），甚至不同的模型/供应商。

让 A 模型写、B 模型审，比同一个模型自审有效得多。**自审有严重的自我一致性偏差**：它倾向于认可自己刚生成的推理链。

### 2.2 Fresh context 避免锚定

> subagent 每次都是新鲜上下文，没有历史包袱，也不会被主对话里之前的错误假设「锚定」——这对验证类任务（让一个干净的 agent 复核结论）尤其有价值。

这一条正中痛点。AI 写错代码的典型模式是**顺着自己的错误假设一路推下去**，带上下文的自审会沿同一思路走，所以看不出问题。干净上下文的审查者看不到"作者的思路"，只看代码本身，反而更容易挑出问题。

这和人类调试时的困境是同一个道理，可对照 [[Debug 时如何不被思维定势影响]] 里的**锚定效应**：最先看到的信息成了思维锚点，后面推理都绕着它转。

### 2.3 对抗式评审，而不是"评价一下"

[[Claude Code Loop 工程：loop、goal 与 schedule|Claude Code Loop 工程]] 里的组合用法给了范式：

> explore three solutions in parallel worktrees and have a judge adversarially review them.

**让 judge 去攻击方案，而不是给方案打分。** 这是把 review 从"找优点"变成"找反例"，对应 [[Debug 时如何不被思维定势影响]] 中的**主动证伪**——把"我要证明它对"换成"我要找个实验推翻它"。成本低、产出高，而且不容易被漂亮的代码骗过。

## 三、在写之前拦，而不是写完再读

性价比最高的一条：

> 把 agent 当作有能力的协作者。让它给出计划，要求它解释，对你不认可的方案要敢于提出质疑。 —— [[Cursor Agent Best Practice]]

**预审一段 20 行的计划，远比预审 2000 行 diff 便宜。** 而且计划里的错误往往就是 diff 里错误的根源——在计划阶段拦掉，diff 根本不会产生。

配套两条：

- **限制单次改动粒度**：小 diff 才 review 得动。让 agent 分步提交、每步可运行，而不是一次吐一整个重构。
- **控制并行度**：多 worktree 并行的确快（见 [[Cursor Agent Best Practice]] 的并行用法），但并行 N 个 = 产生 N 倍待审代码。**并行度应该由 review 带宽倒推**，而不是由机器上限决定。

## 四、真要读 diff 时的技巧

[[PR Review：单栏与双栏 diff 的选择]] 给了具体做法：

- 修改既有逻辑/条件/参数、大段重写 → **双栏**，便于发现条件丢失、参数变化
- 纯新增、长行、深层缩进 → **单栏**
- 宽屏默认双栏，窄屏默认单栏，再按改动类型切换

> [!warning] 对 AI 代码尤其致命的一条
> "复杂重构要打开完整函数看上下文。两种 diff 都可能把代码切碎；**左右对齐也不代表语义上真正对应**，仍需检查控制流和行为是否符合预期。"
>
> AI 很擅长产出"左右看起来对齐、语义已经跑偏"的重写。所以高危区改动建议**直接读完整文件，不读 diff**。

## 五、兜底与红线

- **条件必须可验证**："`npm test` 全绿且 `git status` 干净" ✅，"改进一下代码" ❌ —— [[Claude Code Loop 工程：loop、goal 与 schedule|Claude Code Loop 工程]]
- **明确审批边界**：merge / deploy / publish / delete 之前必须人工确认
- **留痕**：把进度写到文件或 PR comment，让下一个 turn 有持久状态

> [!danger] 不可 review 就不合并
> 如果一个 AI 改动你**既没有验证信号、也没时间读、又不敢不合并**——答案是**不合并**。
> 留在分支上不丢人，合进去才丢人。

---

## 速查清单

> [!summary] AI 产出堆起来时，按顺序问自己
>
> 1. 这个改动有可验证信号吗？没有 → 先补测试，别读代码
> 2. 它属于哪一档？机械 / 一般 / 高危？高危才逐行读
> 3. 能不能派一个 **fresh context + 异构模型**的 subagent 去审？
> 4. 我是在审计划还是在审 diff？能前移到计划阶段吗？
> 5. 这个 diff 我能否拆得更小、并行度能否调低？
> 6. 读 diff 时，我有没有被"左右对齐"骗过？要不要看完整函数？
> 7. 现在这个改动，敢不敢 merge？

> [!tip] 默认选择
> 宽屏默认双栏，窄屏默认单栏，再按改动类型切换。以下是阅读上的经验建议，不是固定规则。

## 两种视图适合回答什么问题

- **单栏（Unified）**：删除行和新增行在同一栏依次展示，便于连续阅读改动，理解“这段改动整体在做什么”。
- **双栏（Split）**：旧代码在左、新代码在右，便于对照“原来怎样，现在怎样”，减少记住旧实现再上下滚动比较的负担。

## 按场景选择

| 场景 | 更推荐 | 原因 |
| --- | --- | --- |
| 修改既有逻辑、条件、参数 | 双栏 | 便于发现条件丢失、参数变化等细节 |
| 大段替换、函数重写 | 双栏 | 可以同时查看旧实现和新实现 |
| 新增文件、大量纯新增代码 | 单栏 | 连续阅读更顺畅，宽度利用更充分 |
| 长行、深层缩进、Markdown 段落 | 单栏 | 减少折行和横向滚动 |
| 笔记本分屏、旁边还开着编辑器 | 单栏 | 每栏过窄会抵消并排比较的优势 |

## 实际 review 时的切换习惯

1. 先用适合当前屏幕宽度的默认视图通读，遇到难以对照的替换块就切双栏。
2. 双栏一旦频繁需要横向滚动，就切单栏，不必为了保留双栏而把字号缩得很小。
3. 复杂重构要打开完整函数看上下文。两种 diff 都可能把代码切碎；左右对齐也不代表语义上真正对应，仍需检查控制流和行为是否符合预期。

如果需要追溯旧逻辑为什么这样写，可结合 [[git 常用命令#查看单个文件的修改历史]] 中的 `git log -p`、`git show` 和 `git blame`。

## GitHub 中的设置

在 PR 的 **Files changed** 页通过 diff 视图菜单选择 Unified 或 Split。GitHub 会记住该选择并应用到其他 PR，因此可以把最常用的屏幕布局作为默认。

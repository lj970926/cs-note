> [!quote] 核心认知
> **读源码不是读书，是破案。** 目标不是"读完"，而是带着一个具体问题，用最少的代码量把答案挖出来。通读是读大型项目最大的陷阱——代码是网状的，不是线性的。

---

## 一、先诊断：你这次读源码要解决什么

> [!question] 打开代码前问自己
> 不同的目的，读法完全不同：

| 目的 | 策略 | 验收标准 |
| --- | --- | --- |
| **解一个具体 bug / 行为** | 从症状反推调用栈，只读路径上的代码 | 能复述"输入 X 为什么变成 Y" |
| **加一个 feature** | 找到同类已有功能，照猫画虎读它的全链路 | 能写出"改动点清单"（文件 + 函数） |
| **理解整体架构** | 读入口 + 核心数据结构 + 主循环，画一张图 | 能给别人讲清楚 10 分钟版本 |
| **评估/选型** | 只读接口边界和配置项，不深入实现 | 能列出能力边界和限制 |

没有目的就开读，90% 会迷失在细节里。

---

## 二、建地图：先拿到全局结构再下钻

> [!tip] 先画地图，再行军
> 花 10% 的时间建立全局认知，能省 50% 的迷路时间。

- [ ] **读 README / docs / 配置项**：官方文档告诉你作者"希望你怎么理解这个项目"，配置项列表往往就是能力边界的目录。
- [ ] **找入口和主循环**：`main()`、server 启动流程、事件循环。从入口顺着走一遍，知道"请求的一生"经过哪些大模块。
- [ ] **识别核心数据结构**：大型项目通常有 2~5 个"枢纽对象"（如 vLLM 的 `Request` / `KVCacheManager`、brpc 的 `bthread`）。枢纽对象的字段和成员函数清单，就是架构的骨架——值得为它们画 class diagram。
- [ ] **看目录命名和依赖方向**：目录名是作者的模块划分声明；谁依赖谁决定了分层。测试目录（`tests/`）是免费的"模块用法说明书"。

## 三、下钻：带着问题沿调用链走

- [ ] **从一个可观察现象出发**：一个 CLI 参数、一条日志、一个 metric 名、一个报错字符串。全局搜索它，就找到了代码里的"锚点"。
- [ ] **双向往返**：从锚点向上找"谁调用它"（理解触发条件），向下找"它调用谁"（理解实现机制）。一次只沿一条链走，走完再换。
- [ ] **读接口不读实现**：遇到非路径上的依赖，只看函数签名和 docstring，假设它是对的。只有怀疑它时才展开——**怀疑驱动深入，好奇驱动收藏**。
- [ ] **用 debugger 代替脑内执行**：对复杂控制流（异步、回调、线程切换），下个断点跑一遍真实 case，看实际调用栈，胜过静态读一小时。
- [ ] **读测试用例**：测试是"最小可运行示例"，告诉你这个模块的典型输入输出和边界情况。

> [!warning] 常见迷路信号
> 打开的文件超过 15 个 tab、开始读第三层以下的工具函数、笔记里抄代码多于写结论——停下来，回到你的原始问题。

## 四、固化：边读边产出，防止白读

> [!tip] 笔记不是摘抄，是压缩
> 好的源码笔记 = 一句话定义 + 一张图 + 关键路径上的文件:行号清单。

- [ ] **一句话定义**：读完一个机制，先逼自己写"它是什么、解决什么问题"的一句话版本（参见 [[DBO 源码梳理]] 第 0 节的写法）。
- [ ] **画图代替抄代码**：class diagram 画枢纽对象关系，sequence diagram 画关键流程。图逼你抽象，抄代码不会。
- [ ] **记锚点不记全文**：`文件:行号` + 一句注释，比重读时重新搜索快得多。
- [ ] **写"前提与限制"**：每个机制记下它的启用条件和不支持的场景（如"DBO 只支持 DeepEP 后端 + Full CUDA Graph"）——这是最容易忘掉、也最有复用价值的部分。

## 五、节奏：对抗"太大读不完"的瘫痪感

- [ ] **时间盒代替结果盒**：不定"今天读完 KV Cache 管理"，定"下午两小时只追 `allocate_slots` 这一条链"。
- [ ] **烂开始原则**：第一版理解允许是错的。先建立假说，再用代码验证/推翻，比追求"一遍读懂"快得多。
- [ ] **分层放弃**：明确告诉自己"这次只读到调度层，kernel 实现不进"。读源码的深度是自己选的，不是项目强加的。
- [ ] **卡壳就换证据源**：静态读不懂 → 跑起来看日志 → 打断点 → 翻 git blame 看这段代码为什么被改成这样 → 翻对应 PR 讨论。代码看不懂时，历史往往比现状更好懂。

## 六、借力：把 LLM 当结对读码搭子

> [!quote] 核心认知
> **LLM 改变的是"建地图"和"下钻"的成本结构，不改变"带着问题读"的原则。** 它擅长压缩和导航，不擅长替你形成判断——没验证过的 LLM 结论，一律按假说处理。

### 适合交给 LLM 的事

- [ ] **冷启动建地图**：让 agent 扫一遍仓库，输出"入口在哪、主循环是什么、枢纽数据结构有哪几个"。相当于把 §2 的工作从半天压到十分钟，但结论要抽查。
- [ ] **语义级锚点搜索**：ripgrep 只能搜字符串，LLM 能搜"负责 KV block 回收的逻辑在哪"这种语义问题，直接给 `文件:行号` 清单。
- [ ] **单文件/单函数压缩**：贴一个 800 行文件让它输出"这个类对外承诺什么、内部状态怎么流转"，先读压缩版再决定要不要读原文。
- [ ] **跨语言/陌生领域的翻译器**：读 CUDA kernel、Rust 生命周期、不熟的框架惯例时，让它逐段解释"这段在干嘛、为什么这么写"，比自己查文档快。
- [ ] **追问式理解**：读完一段后对 LLM 复述自己的理解，让它挑错——"我认为这个锁保护的是 X，对吗？" 比让它直接讲更能暴露自己的盲区。
- [ ] **生成图和笔记初稿**：让它按你的笔记格式产出 class diagram / 一句话定义初稿，自己只做校对和修正（参见 §4，画图的成本被大幅压低）。

### 必须自己做的事

- [ ] **提出问题和验收标准**：§1 的诊断没法外包。LLM 不知道你为什么要读，"帮我看看这个项目"得到的只能是正确的废话。
- [ ] **验证关键结论**：涉及行为语义的核心判断（并发正确性、内存生命周期、边界条件），必须自己读原文或打断点确认。LLM 对"代码实际行为"会自信地编造。
- [ ] **读历史动机**：`git blame` / PR 讨论里"为什么改成这样"的 trade-off，LLM 看不到上下文，问了也多半是脑补。

> [!warning] 三个典型翻车姿势
> - **整仓投喂求总结**：上下文装不下，得到的是基于文件名和 README 的合理想象，不是基于代码的结论。
> - **用 LLM 结论替代验证写进笔记**：笔记里混入未验证的编造，比没有笔记更糟——它会污染未来的你。
> - **把下钻也外包**：只读 LLM 的压缩版，永远不读原文，久而久之失去对细节的体感，遇到 LLM 答不上的深水区问题就没有退路了。

> [!tip] 推荐循环
> **LLM 建地图 → 自己定问题 → LLM 找锚点 → 自己读原文验证 → LLM 协助成图成稿 → 自己校对结论**。LLM 在每步做压缩和导航，人始终握着"问题"和"验收"两头。

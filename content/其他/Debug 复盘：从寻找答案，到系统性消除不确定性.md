# Debug 复盘：从寻找答案，到系统性消除不确定性

> **核心结论：优秀的 Debugger 不一定是想到最多可能性、读过最多代码的人，而是能够以最低的合理成本，持续缩小问题空间的人。**

## 一、背景：一次值得反思的 Debug 经历

在一次 LLM Inference / Serving 问题排查中：

- 问题比较复杂，相关代码也不够熟悉。
- 自己提出过很多可能的原因，包括最终的正确方向。
- 因为深入阅读代码的成本高，而且希望尽快解决问题，倾向于寻找更简单的解释。
- 排查方向不断增加，在不同假设之间切换，最终没有找到根因。
- 另一个 AI Agent 从数据集中抽取了几条 Bad Case，围绕具体问题深入代码，最终定位了 Bug。

得知结果时，第一反应是遗憾：**「这个方向我明明想到过，为什么当时没有继续查下去？」**

这次经历暴露的主要问题，可能不是技术水平不足，而是复杂问题下的注意力管理、调查策略和不确定性决策。

# 第一部分：道——思维方式与认知

## 1. Debug 的本质是消除不确定性

Debug 不应该被理解为不断寻找 Bug，而应该被理解为：

**通过证据，逐步缩小导致异常的可能性空间。**

衡量一次排查行动是否有效，不应该只看有没有直接找到 Bug，还应该看：

- 是否排除了一批可能性？
- 是否提高或降低了某个假设的可信度？
- 是否把抽象问题转化成了更具体的问题？
- 是否为下一步调查提供了明确方向？

读了大量代码、产生很多假设，不等于排查取得了实质进展。

**思考的数量不等于信息增益。**

## 2. 不要把「想到了」误认为「已经接近解决」

提出正确假设和证明正确假设，是两种不同的能力。

一次成功的 Debug 至少包含三个环节：

1. **发现假设**：什么机制可能导致异常？
2. **获取证据**：如何证明或排除它？
3. **建立因果链**：为什么这个机制必然或可能导致观察到的结果？

曾经想到正确方向，说明技术直觉覆盖到了真正的根因；没有完成验证，说明假设尚未转化为知识。

要警惕事后偏差：知道答案后，很容易高估当时线索的明显程度。

真正应该复盘的是：**以当时掌握的信息，怎样才能做出更合理的下一步决策？**

## 3. 不要让「追求效率」变成「逃避困难」

这次经历最值得警惕的心理循环：

发现可疑方向 → 觉得深入成本太高 → 寻找更简单的解释 → 产生更多可能性 → 注意力分散 → 缺乏深入验证。

每次切换都似乎合理，但整体可能越来越低效。

这里必须区分两件事：

- **寻找更便宜的验证方法**：优秀的工程策略。
- **因为验证成本高而不断回避高价值假设**：需要克服的倾向。

不要因为一个方向难查，就默认它不值得查。

也不要走向另一个极端：对最初的直觉过度执着。

正确的方法是基于证据价值、验证成本和预期信息增益，决定何时深入、何时切换。

## 4. 深度思考不等于同时思考很多问题

复杂系统往往存在大量潜在原因，特别是并发、缓存、调度、异步执行等场景。

如果同时在脑中维护架构、调用链、多个假设、实验结果和未验证的可能性，工作记忆很容易超载。

需要建立两个习惯：

- **外部化思考**：把假设、证据、未解决问题写下来，而不是全部保留在脑中。
- **控制进行中的调查数量**：可以同时保留很多假设，但每次只重点推进一到两个。

有时候，真正的深度思考不是产生更多方向，而是忍住切换方向的冲动，追问当前证据到底意味着什么。

## 5. 追求过程质量，而不只是结果

不能因为最终没查出 Bug，就断言之前所有决策都是错误的。

同样，偶然找到 Bug，也不代表方法正确。

应该评价的是：

**每一步行动，在当时的信息条件下，是否是合理的选择？**

长期来看，稳定的方法论比一次成功更有价值。

# 第二部分：术——具体 Debug 方法论

## 6. 优先从具体失败出发，而不是从大范围源码出发

这次 Agent 最有启发性的做法，就是先从数据集中抽取 Bad Case。

两种调查路径的区别：

**容易陷入的路径：**

整体指标异常 → 提出很多假设 → 阅读大量代码 → 尝试寻找 Bug。

**更值得优先采用的路径：**

整体指标异常 → 提取代表性 Bad Case → 对比正常与异常行为 → 缩小执行路径 → 针对性阅读代码 → 验证根因。

核心原则：

**先让问题具体化，再让代码阅读目标化。**

例如 pass@5 从 42 降到 38，比起直接深入整个 Prefix Cache 实现，可以先比较配置 A/B 下哪些样本的结果发生变化。

尤其关注：

- 哪些 Case 具有稳定、明显的差异？
- 它们有没有共同特征？
- 异常是否和请求长度、Prefix Cache Hit、并发、历史请求有关？
- 最早发生分歧的位置在哪里？

注意：对于缓存、调度、竞态等有状态问题，一个 Bad Case 可能不是单条请求，而是一段需要保留请求顺序、缓存状态或并发条件的执行历史。

因此，**Bad Case 提取不等于最小复现**，最小化输入时必须保留触发条件。

## 7. 用实验决定读哪段代码

陌生代码读起来成本很高，但并不意味着必须先完全掌握相关模块。

采用分层调查：

**Level 1：黑盒实验**

通过开关配置、控制输入、对照运行和日志收集，判断哪些条件与异常相关。

**Level 2：灰盒追踪**

围绕具体 Bad Case 追踪调用路径、关键状态和数据流，寻找首次出现异常的位置。

**Level 3：白盒深入**

深入理解具体实现、不变量、生命周期和状态交互，确认根因并修复。

原则是：**不要一直停留在黑盒层，也不要在没有具体目标时贸然深入白盒层。**

实验设计的核心指标不是简单与否，而是：

> 单位调查成本能够带来多少信息增益？

## 8. 建立假设管理机制

每个有价值的怀疑至少记录三个东西：

| 假设 | 证据或下一步实验 | 当前状态 |
|---|---|---|
| Prefix Cache 状态异常 | 关闭后异常消失；追踪缓存复用路径 | 高优先级 |
| CUDA Graph 相关异常 | 对比启用与关闭行为 | 待验证 |
| Sampling 配置导致差异 | 固定参数及随机性后做 A/B | 待验证 |

对状态做严格区分：

- **已证实**：有证据支持明确结论。
- **暂时排除**：特定条件下的实验与该假设不符。
- **未验证**：还没有足够证据判断。

最忌讳的是：

**把「我看过但没发现问题」，当成「这个方向已经排除」。**

对于验证成本较高的假设，记录它需要哪些证据，而不是简单放弃。

## 9. 建立「停止发散，开始深入」的机制

当某个方向满足以下条件时，应当显著提高深入排查的优先级：

- 已有直接实验现象支持。
- 多个低成本替代假设已经被削弱。
- 继续寻找新方向的收益开始下降。
- 能够围绕该方向构造更具体的复现或追踪实验。

可以设置有限的调查时间，例如先用 20～30 分钟设计和运行高区分度实验，然后重新评估。

时间限制的作用不是强迫切换，而是防止无意识地持续发散或陷入无效阅读。

**每次切换方向之前，都应该明确：为什么当前方向不再是最值得投入的？**

## 10. 利用 AI Agent 降低深入调查的成本

Agent 的最大价值不只是快速搜索源码，而是降低验证复杂假设的成本。

合理的职责划分：

**工程师负责：**

- 定义问题、异常指标和正确性标准。
- 选择代表性 Bad Case。
- 判断哪些假设有价值。
- 设计有区分度的实验。
- 审核根因解释与修复方案。

**Agent 负责辅助：**

- 搜索陌生代码、梳理调用链。
- 跟踪关键状态与数据结构。
- 基于 Bad Case 提出具体根因假设。
- 编写调试日志、复现脚本和测试。
- 对比不同实现路径。

不要等自己把所有代码读懂以后才让 Agent 参与。

但也不能把 Agent 给出的解释直接当成最终事实。应该要求它提供具体代码位置、触发条件、因果机制和可验证的证据。

**Agent 可以降低调查成本，但不能替代工程判断。**

## 11. 熟悉代码仍然重要，但要改变熟悉的目标

AI 时代，熟悉代码的价值可以分为两个层次。

**第一层：实现细节**

函数位置、调用链、具体字段、模块组织。

这部分可以越来越多地借助 Agent。

**第二层：系统模型与不变量**

例如：

- KV Cache 的状态必须满足哪些约束？
- Prefix Cache 什么时候可以安全复用？
- Scheduler 与 Worker 之间有什么同步要求？
- 什么情况下缓存的逻辑正确性可能被破坏？

第二层的价值依然很高，因为它决定技术直觉、实验设计、根因判断以及修复可靠性。

因此，平时优先理解系统设计、状态生命周期和关键不变量；Debug 时按需深入具体实现。

**Debug 方法论 ≈ 系统理解能力 > 单纯记忆代码实现细节。**

这不是否定阅读源码，而是让阅读源码具有明确目的。

# 第三部分：形成自己的 Debug 工作流

## 12. 一套可重复使用的七步流程

**Step 1：定义问题**

明确期望行为、实际行为、影响范围和观测条件。

**Step 2：抽取代表性 Bad Case**

寻找失败样本，尤其是对照配置下具有稳定差异的样本。

**Step 3：构造可复现的实验**

固定必要参数与环境；对有状态问题保留请求历史、缓存及并发条件。

**Step 4：建立并排序假设**

依据现有证据、验证成本与信息增益进行优先级排序。

**Step 5：优先做高区分度实验**

用实验缩小范围，再决定深入哪些代码。可尽早使用 Agent 辅助。

**Step 6：建立完整的因果解释**

明确什么条件触发了哪段机制，进而如何导致异常输出。

**Step 7：验证修复并回归**

确认 Bad Case 得到修复，整体 Benchmark 改善，且没有引入其他问题。尤其注意不能仅用几条成功修复的样本证明整体根因成立。

## 13. 每次 Debug 都值得回答的五个问题

- 我现在掌握的最强证据是什么？
- 哪个实验能最大程度缩小问题范围？
- 我是不是因为某个方向太难，就下意识地回避它？
- 我现在是在获取新证据，还是只是在产生更多猜测？
- 如果现在切换方向，我有没有明确的理由？

# 第四部分：长期成长

## 14. 真正值得培养的三种能力

**第一：问题具体化能力**

将模糊的统计异常转化为具体的、可复现的失败行为。

**第二：实验设计能力**

能够用尽量少的实验，区分不同假设，快速缩小搜索空间。

**第三：系统性深入能力**

面对陌生、复杂、调查成本高的代码，能够基于证据持续推进，而不是无意识地逃避或切换。

三者是互补的。

只会深入，容易陷入细节；只会设计实验，可能无法解释底层机制；只会产生假设，容易陷入无休止的发散。

## 15. 对这次经历的最终评价

这次经历不应该简单总结为：

「当时应该再坚持一下。」

因为下次最初怀疑的方向未必正确，盲目坚持也可能浪费大量时间。

更有价值的结论是：

**「当我怀疑一个重要但难以验证的方向时，应该先尝试降低验证成本；如果证据持续指向它，就应当有意识地投入精力深入，而不是不断寻找更容易的替代解释。」**

Agent 通过 Bad Case 找到问题，也提醒我们：复杂问题未必需要从复杂的入口开始。

排查工作应该优先降低问题本身的复杂度，而不是一开始就试图提高自己对所有代码的理解程度。

---

## 最后，写给自己的三句话

**1. 不要用思考的数量衡量进展，要用消除的不确定性衡量进展。**

**2. 不要因为一条路困难就放弃它，要先想办法降低走这条路的成本。**

**3. 不要把 Agent 当成代替自己思考的人，而要把它当成放大自己调查能力的工具。**

最终希望形成的工作方式是：

**证据驱动、实验优先、控制发散、敢于深入、善用 Agent。**

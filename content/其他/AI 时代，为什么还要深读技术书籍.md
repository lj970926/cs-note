# AI 时代，为什么还要深读技术书籍

> [!abstract] 核心观点
> **大模型让获取知识变得廉价，但没有让建立认知体系、形成技术判断力和发展原创思考能力变得廉价。**
>
> 技术书籍的价值正在变化，深度阅读的意义也需要重新理解：读完一本书之后，你是否获得了一种以前没有的、能够解释和预测系统行为的能力？

以前读技术书籍，很大程度上是为了获取知识；现在大模型能够以很低的成本提供解释、举例和代码，并根据你的水平调整讲法。那么，为什么还要花几十个小时读一本《Operating Systems: Three Easy Pieces》或《Computer Systems: A Programmer's Perspective》？

我认为，答案在于区分「得到一个答案」和「拥有理解、检验与质疑答案的能力」。这也延续了 [[不要努力成为一个比 AI 更好的 AI]] 中的思路：学习目标从「会不会做」，逐渐转向「能不能理解、判断和负责」。

## 一、技术书籍的价值正在发生转移

可以把技术学习分成四个层次。这是一种帮助思考的划分，实际学习中它们往往相互交织。

| 层次 | 核心问题 | 主要作用 |
| --- | --- | --- |
| 获取知识 | 概念是什么，API 怎么使用，算法如何实现？ | AI 擅长提供按需解释与示例 |
| 建立知识体系 | 知识之间有什么依赖，领域的整体地图是什么？ | 精心组织的书籍能提供框架 |
| 形成判断力 | 什么时候该使用什么技术，前提和代价是什么？ | 需要实践、反馈与反思 |
| 创造新知识 | 现有方案哪里有问题，能否提出新的抽象、设计与优化？ | 需要深度思考与验证 |

在 AI 出现之前，这四层往往捆绑在一起：必须阅读大量材料，才能逐步形成理解。现在，第一层的获取成本大幅下降，但得到解释并不自动意味着已经掌握。

如果一本技术书籍只能提供可以随时查询的事实，它的通读价值可能下降。反过来，能够帮助建立系统性思维的书籍，其价值会更加突出。

## 二、读书的重要意义：建立自己的心智模型

以大模型推理系统为例。假设观察到一个现象，并向 AI 提问：

> 为什么 vLLM 开启 Prefix Cache 之后，模型的精度可能发生变化？

AI 可能列出一组排查假设：

- KV Cache 内容或生命周期的正确性问题。
- Block Hash 的计算或匹配问题。
- Cache 复用时的 Position / RoPE 处理问题。
- 不同执行路径引入的数值差异。

这些只是候选解释，不是已经确认的根因，也不意味着开启 Prefix Cache 必然影响精度。关键问题是：**凭什么判断解释是否成立，哪个假设最值得优先验证？**

这取决于脑海里是否已经有一个关于推理系统的模型：Attention 数学、KV Cache 生命周期、PagedAttention 内存映射、连续批处理调度、CUDA Kernel 数值行为，以及它们之间的依赖关系。

有了这样的模型，AI 提出的假设就能映射到具体机制、前提和可观察证据上。缺少模型时，可能只能逐条尝试，甚至不知道它是否遗漏了关键问题。

阅读经典技术书籍的意义之一，是让自己拥有**组织、检验和质疑答案的能力**。这种能力也能通过深入阅读源码、做实验和调试生产问题建立，往往还能获得更加直接的反馈。

[[大型项目源码阅读方法论]] 强调先建地图、再带着问题下钻；[[Debug 复盘：从寻找答案，到系统性消除不确定性]] 则提醒：提出假设之后，还需要获取证据并建立因果链。它们与系统性阅读可以互相补充。

## 三、书籍让你接触「不知道自己不知道的知识」

按需问答有一个局限：问题很容易受到当前任务和已有认知的限制。

例如学习分布式系统时，可能会问：什么是 Raft？它与 Paxos 有什么区别？如何保证一致性？但如果没有接触过相关领域，可能根本不知道还应该研究：

- Failure Detector（故障检测器）。
- Linearizability（线性一致性）。
- Safety 与 Liveness（安全性与活性）。
- Fencing Token。
- Byzantine Fault（拜占庭故障）。
- Distributed Snapshot（分布式快照）。

AI 也可以生成学习路线、主动提示盲区。这里的局限主要来自始终采用「遇到问题 → 提问 → 得到答案」的学习模式，而不是 AI 只能被动回答。

一本经过精心组织的技术书籍，提供了作者对领域的知识结构、问题选择和推理顺序。它不仅提供答案，也让读者知道：**这个领域究竟有哪些重要的问题。**

## 四、阅读方式也需要改变

我更倾向于这样的组合：

> **书籍提供认知框架，AI 提供交互式解释，实践负责验证理解。**

例如阅读《Designing Data-Intensive Applications》，可以做如下调整：

| 常见阅读方式 | 更值得尝试的做法 |
| --- | --- |
| 顺序阅读每一章 | 先理解章节要解决的核心问题，再决定阅读顺序和深度 |
| 不理解就反复阅读 | 让 AI 从不同角度解释，再回原文核对前提与边界 |
| 把重要概念整理成笔记 | 尝试不看资料重建概念之间的联系，再查漏补缺 |
| 做书后的练习 | 结合练习，设计实验验证书中的结论 |
| 追求读完一本书 | 追求掌握几种可迁移的思维模型 |

这些方法也可以与顺序精读、练习和复习结合，具体取决于当前基础和学习目标。

对于工程技术，**能否在明确前提下预测系统行为**，是很好的理解标准：

- 理解 CPU Cache Coherence 后，能分析多线程程序在什么访问模式下可能出现严重的 False Sharing。
- 理解 GPU Memory Hierarchy 后，能对 Kernel 的性能瓶颈提出有依据的预测，再用测量检验。
- 理解 LLM Serving 的调度和 KV Cache 管理后，能分析不同负载下吞吐和延迟为什么变化。

预测不要求次次正确。更重要的是能说明依据，并在结果不符时修正模型。这比准确背诵概念更能检验理解。

## 五、警惕技术能力的「空心化」

AI 能帮助一个人实现超出现有理解范围的系统，这是生产力的进步。同时，也可能出现这样的能力结构：

- 能借助 AI 修改复杂的 CUDA Kernel，却无法解释修改为什么正确。
- 能让 Agent 修复 vLLM 的 Bug，却不具备判断根因和验证修复的能力。

如果目标是交付结果，AI 可以成为能力的一部分。但如果目标是成为高级系统工程师、技术专家，乃至设计新的推理框架，那么缺少底层模型与验证能力，可能限制进一步成长。

创新往往要求在现有答案之外继续推理。仅能选择一个看起来合理的答案，还不够。

我也不认为必须「不用 AI 独立完成」才算理解。更实际的标准是：即便方案由 AI 提出，自己是否能够：

1. 审查正确性，识别关键前提和边界条件。
2. 解释原理，说明为什么这样做。
3. 在方案失败时，设计有效的验证实验。

这也呼应了 [[不要努力成为一个比 AI 更好的 AI]] 中「把 AI 当能力外骨骼，但不要把脑子整个外包」的原则。

## 六、什么书值得深读？

我会用一个标准：**一本书越能改变思考方式，而不只是增加知识点，就越值得深读。**

对于 AI Infra 方向，我看重这些书所提供的分析视角：

| 书籍 | 希望获得的思维方式 |
| --- | --- |
| Computer Systems: A Programmer's Perspective | 建立软件与硬件之间的整体联系 |
| Operating Systems: Three Easy Pieces | 理解资源抽象、并发与系统设计 |
| Designing Data-Intensive Applications | 分析系统设计取舍与故障模型 |
| Computer Architecture: A Quantitative Approach | 建立以数据、瓶颈和成本为中心的架构思维 |

这些书的长期价值，在于其中分析方法的迁移性。具体框架的 API 使用手册、某个版本的配置教程，则更适合结合 AI 和官方文档按需学习。

这是一种选书与分配精力的个人标准，不意味着需要通读上述所有书籍。

## 七、用能力变化衡量阅读，而不是用数量衡量成长

在 AI 时代，深度阅读可能逐渐更多地承担训练独立思考的作用。计算器降低了手工计算的必要性，却没有消除理解数学的价值；AI 的影响更广，它已经进入解释、推理、编程和部分技术决策的过程。

我倾向于认为，优秀技术人员需要不断训练这样的循环：

**提出好问题 → 构建合理的系统模型 → 利用 AI 探索方案 → 设计实验验证 → 形成新的认识。**

读技术书籍，是训练其中构建系统模型与深入思考能力的一种高质量方式。源码、实验和真实系统问题，则让这些模型经受检验。

如果一个人每年读 20 本技术书，却很少用于实际问题；另一个人只读 2 本，但长期借助 AI、源码和实验深入研究真实系统，我很可能认为后者的学习效果更好。

因此，我不认为应该以「读完多少本书」衡量技术成长。真正值得追求的是：

> **读完一本书之后，你是否获得了一种以前没有的、能够解释和预测世界的能力。**

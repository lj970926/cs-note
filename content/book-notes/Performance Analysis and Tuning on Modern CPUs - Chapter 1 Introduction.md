# Performance Analysis and Tuning on Modern CPUs —— Chapter 1 Introduction

> [!abstract] 本章主旨
> 单线程性能不再能靠新一代硬件自动大幅提升，程序也不会因为用了高级语言、现代编译器或渐进复杂度更优的算法就自然达到硬件上限。性能工作要先明确目标，再用测量和分析找到真实瓶颈，结合对 CPU 的心智模型做有依据的改动，并验证收益是否值得工程成本。

## 1. 本章回答的问题

- 软件为什么仍可能远低于硬件的潜在性能？
- 性能为何会影响用户体验、产品成本和能源消耗？
- 性能分析与性能调优各自解决什么问题？
- 怎样判断何时开始、继续或停止优化？
- 本书覆盖哪些问题，又有哪些问题不在范围内？

## 2. 软件性能为何不理想

硬件快速执行指令，但它只会执行程序交给它的工作。若算法本身做了大量不必要的工作，CPU 不会自动把它换成更好的算法；因此，性能差距不能简单归咎于处理器不够快。

常见限制可分为四类：

1. **硬件不会替程序改算法。** Bubble sort 即便运行在很快的 CPU 上，也仍然按其算法特征工作。
2. **编译器受启发式、正确性证明和成本模型限制。** 编译器能消除不少冗余，但向量化、内联等变换需要结合具体场景权衡；它通常不会冒险做无法证明安全的改写，也很少大规模重构程序的数据结构。
3. **渐进复杂度没有包含硬件成本。** Big O 不反映常数、数据规模、缓存未命中和分支预测失败等因素。例如小规模输入上，简单算法有时胜过渐进复杂度更好的方案。算法选择仍要对目标输入和机器实测。
4. **抽象与通用性可能带来运行时成本。** 额外的函数调用、动态分派、运行时检查、内存分配或数据拷贝可能影响关键路径。可读性和可维护性仍然重要，应该结合测量，在有性能要求的部分看清成本。

书中以矩阵乘法为例展示了巨大优化空间：从高级语言实现到并行、向量化及显式 SIMD，逐步优化后性能可相差多个数量级。这个例子强调的是默认代码并不必然高效，而不是要求每个项目都做手写汇编式优化。

## 3. 为什么要关心性能

- **硬件进步的“自然红利”减弱。** 单线程性能增长放缓后，软件优化成为持续获得性能提升的重要来源。
- **云上低效会变成供应方的成本。** 服务器时间、用电和制冷都会进入运营成本；大规模服务里，小幅提升也会累积为可观的成本和能耗差异。
- **响应速度关系到留存与效率。** 等待会打断用户工作，也可能让客户转向替代产品。低延迟还使交互方式和工具用途成为可能。
- **许多小收益可以叠加。** 单次优化未必显著，但长期持续改进会形成差距；同时，更快或更省资源的代码也可能降低能耗。
- **性能既是专项领域的硬约束，也属于通用软件质量。** AI、HPC、高频交易和游戏等领域对此要求明显；编辑器自动补全等日常功能也需要维持迅速响应。

先给性能工作设定业务或用户价值，再定义可以检验的指标。根据场景，指标可能是延迟、吞吐量、每秒操作数或资源利用率；没有目标和度量标准，“更快”就无法判断，也无法说明优化值不值得。

## 4. 性能分析：找出瓶颈

**性能分析（performance analysis）** 是收集程序运行信息、解释这些信息并据此寻找优化机会的过程。它回答“时间和资源花在哪里、为什么”。

关键做法是先观察，再提出改动：

- 依靠直觉进行微优化容易得到无效改动。看起来更快的写法可能被优化编译器生成完全相同的机器码。
- 过去有效的技巧可能已被编译器吸收；而一些“聪明”的位操作写法也可能不如简单、清楚的标准实现。
- 小改动在现代处理器上可能产生意外影响，所以每次优化主张都应由适当的测量支持。
- 不同问题适合不同分析方法；分析范围可以从小函数扩展到陌生的大型代码库。

## 5. 性能调优：修复并确认

**性能调优（performance tuning）** 是在分析定位问题后，修改实现以消除或缓解瓶颈。分析和调优是性能工作的两个环节：定位问题但不修复不完整；改了代码却不确认瓶颈和收益，则容易变成猜测。

低层调优依赖对硬件工作方式的基本理解，也就是对处理器建立足够准确的“机械同理心”。不需要记住每个微架构细节，但要理解哪些硬件资源和执行特征会影响目标代码。这里的低层优化关注硬件能力；高层优化则更多从应用逻辑、算法和数据结构入手。两者可以互补。

Knuth 的“过早优化是万恶之源”并不意味着可以把性能拖到最后再看。对性能关键的软件，性能、正确性与安全性应从开发早期一起纳入设计和验证；但优化也没有终点，应在预期收益不足以覆盖工程成本时停止。

## 6. 全书路线与适用范围

| 部分 | 章节 | 学习重点 |
| --- | --- | --- |
| 找问题 | 2–7 | 公平测量、CPU 微架构、性能指标、分析方法、处理器分析功能及平台工具 |
| 解决问题 | 8–13 | 内存访问、计算与向量化、分支预测、机器码布局、其他调优主题及多线程分析 |

本书重点关注单 CPU socket 上、面向现代 CPU 的用户态原生代码性能，内存子系统也有较多讨论。示例主要使用 Linux、Clang、C/C++、开源软件与基准，也会使用 Intel VTune。许多思路可迁移至其他操作系统和编译为原生代码的语言，例如 Rust、Go 和 Fortran。

明确不覆盖的范围包括：I/O 与网络性能、分布式与 NUMA 系统、多 socket、异构系统和 GPU/FPGA 加速；也不以托管运行时（如 Java）或调优无法控制的商业软件包为目标。实际工程排查仍应先看整套系统，因为瓶颈未必总在 CPU；本书的范围只是聚焦 CPU 侧的方法。

```text
硬件单线程性能增长放缓
        ↓
默认代码、编译器和渐进复杂度都不能保证贴近硬件上限
        ↓

```

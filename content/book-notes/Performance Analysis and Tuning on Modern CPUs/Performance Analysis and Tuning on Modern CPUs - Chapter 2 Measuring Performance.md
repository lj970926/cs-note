# Performance Analysis and Tuning on Modern CPUs —— Chapter 2 Measuring Performance

> [!abstract] 先记住这一句
> **跑出一个数字很容易，证明这个数字可信很难。** 同一段代码每次跑的快慢都可能不同。要判断一次优化有没有用，需要公平比较、多测几次、看结果怎么分布，还要能解释为什么变快。

前一章：[[book-notes/Performance Analysis and Tuning on Modern CPUs/Performance Analysis and Tuning on Modern CPUs - Chapter 1 Introduction|Modern CPUs Ch.1]]。下面按原书 §2.1–2.7 整理；例子中的演示数据不代表实测结果，计时器的补充辨析另有来源。

## 1. 为什么同一个程序，每次跑得都不一样？（§2.1）

把 benchmark 理解成一场比赛：**代码没变，不代表赛场没变。**

| 干扰来自哪里 | 会发生什么 | 容易得出的错误结论 |
| --- | --- | --- |
| CPU 频率、温度 | 刚空闲过的 CPU 温度低，可能短时间睿频；跑热后可用频率下降 | “先跑的版本更快，所以它写得更好” |
| 缓存状态 | 第一次 `git status` 需要读取文件信息，第二次可能直接命中文件系统缓存 | “第二个版本快很多” |
| 后台任务、系统中断 | 测试中途被别的工作打断，或与其他进程争用资源 | “这次改动让性能突然变差” |
| 代码和数据的内存布局 | 链接顺序、环境变量等变化，也可能间接影响运行速度 | “我只改了无关代码，性能不该变” |

这里要区分两件事：**噪声**让结果忽快忽慢；**测量偏差（bias）**让某个版本持续占便宜。例如总让 A 在冷 CPU 上跑、B 在热 CPU 上跑，即使重复很多次，也可能一直偏向 A。

**多跑几次，不能自动修复不公平的实验。**

### 该不该关睿频、清缓存、做预热？

先看你想回答什么：

- **想判断一个小改动本身有没有收益**：尽量控制机器、编译选项、后台负载、频率和缓存状态，让前后版本在相近条件下比较。
- **想知道用户实际会不会觉得更快**：尽量接近真实使用环境。用户开着睿频、旁边跑着别的服务，你的实验也要考虑这些条件。

预热也是同样的道理：测稳定运行时，可以先预热；测启动或首次访问时，冷启动本来就是要测的成本，不能删掉。

> [!tip] 不用追求“绝对安静”的机器
> 先消除主要干扰，做到结果足以支持当前判断。继续降噪的成本可能越来越高，而真实环境本身就有波动。

## 2. 实验室里更快，线上也可能更慢（§2.2）

实验室通常输入可控、资源充足；线上可能有不同的数据、用户设备，以及争抢 CPU、缓存和内存的邻居进程。**实验室测试提供线索，最终还要看真实负载。**

例如，一个实现用更多内存换速度，在独占机器上可能获胜；放进拥挤的服务器后，内存压力甚至换页可能把收益吃光。这也是原书后面讨论微基准时提醒的问题。

所以需要两层观察：本地或 CI 测试帮你尽早发现问题，生产监控帮你确认用户实际遇到什么。

监控也要花资源。书中提到，持续 profiling 通常追求低于 1% 的总体开销；这是设计目标的参考，不是所有业务的统一标准。可以只采一部分机器、降低采样频率，避免为了观察服务而明显拖慢服务。

## 3. 性能也要防“回归”：别等慢了一大截才发现（§2.3）

**性能回归（regression）**就是新版本功能还对，但比以前慢了。

最基本的办法是：固定测试配置，持续跑代表性 benchmark，把结果和提交版本一起存下来，画成趋势图，异常时提醒。

### 为什么“慢超过 2% 才报警”还不够？

阈值小了，噪声也会报警；阈值大了，小退步容易漏掉。比如每天退步一点，每次都不到 2%，十天下来已经慢了一截，系统却从没响过。

原书介绍两种思路：

| 方法 | 人话解释 | 适用场景与代价 |
| --- | --- | --- |
| 固定阈值 | “比基线慢超过某个比例就提醒” | 简单、反馈快；适合波动小、需要立即判断的测试，但阈值难选 |
| 变点检测（CPD） | “看最近一段结果，是偶然抖了一下，还是整体换了个水平？” | 能结合历史减少误报；通常需要后续几个点确认，反馈会晚一些 |

例如耗时一直在 5–7 秒之间，突然跑出一次 11 秒，未必已经退步；后面又连续跑出 10 秒、12 秒，就更值得调查。

**机器配置、编译器或测试条件变了，要标出来。** 否则图上看到的变化，可能来自环境而非代码。

> [!warning] 突然变快，也要查原因
> 如果一个看似无关的提交快了 10%，可能是好事，也可能是某部分工作被跳过了，而功能测试刚好没覆盖。性能测试也能帮忙发现正确性问题。

## 4. 手动比较前后版本：看一组结果，别押宝一次计时（§2.4）

先确认两个版本完成相同的工作，再分别运行多次。你比较的是**两组测量结果的分布**。

### 平均值为什么可能骗人？

假设五次耗时是：

```text
100 ms、101 ms、99 ms、100 ms、500 ms
```

平均值是 180 ms，中位数是 100 ms。

这两个数回答的问题不同：大部分运行在 100 ms 左右，但确实出现了一次很慢的运行。只报平均值，会看不出这个形状；只报中位数，又可能忽略慢请求。

| 指标 | 你可以把它理解成 |
| --- | --- |
| 平均值（mean） | 总耗时摊到每次是多少；容易被特别慢的样本拉高 |
| 中位数（p50） | 排序后处在中间的位置；典型一次大致是什么水平 |
| p95 / p99 | 约 95% / 99% 的样本不超过这个耗时；关注慢的那一端 |
| 标准差 | 结果有多分散；越大说明波动越明显，不能只盯平均值 |

书中 Figure 2.3 用箱线图比较前后版本，每组有 70 个样本：箱子覆盖中间 50% 的数据（p25 到 p75），箱内横线是中位数。**一眼看整体位置和分散程度，比只看两个平均值更有信息。** 图里标出的 min/max 不包含被单独画出的离群点。

不需要现在就学完整统计学，但如果声称“快了 1%”，结果本身却大幅波动，就还需要更强的证据。

### “快了多少”要说清楚口径

同样的工作，从 10 秒降到 8 秒：

- **加速比**：旧耗时 ÷ 新耗时 = 10 ÷ 8 = **1.25 倍**。
- **耗时减少比例**：（旧耗时 − 新耗时）÷ 旧耗时 = 2 ÷ 10 = **20%**。

别把“1.25 倍加速”写成“耗时减少 25%”。对于相同工作量，处理速率提高和耗时减少用的分母不同。

### 多测多少次才够？异常点能删吗？

没有通用的“跑满 N 次就可信”。书中说，昂贵的长测试可以先看三次；如果已经很稳定，继续堆样本的边际收益可能不大。**这是节省测试成本的经验，不代表三次就能可靠估计 p99 或证明微小收益。**

如果三次就抖得很厉害，先找干扰来源，别指望多跑一百次就自然变准。

异常点也不能因为“不好看”就删：测稳态时，可以按事先确定的规则把预热单独处理；测用户响应或实时任务时，极慢的那几次可能正是最重要的问题。

## 5. 用什么计时？先用单调时钟，短到不够用再考虑 TSC（§2.5）

### 两种计时方式，像“标准秒表”和“直接读硬件刻度”

| 方式 | 读到什么 | 什么时候用 |
| --- | --- | --- |
| 系统计时接口，例如 C++ `std::chrono::steady_clock` | 已经换算好的时间 | 大多数日常耗时测量，默认先选它 |
| x86 TSC，例如 `__rdtsc()` | 硬件计数器的 tick | 极短代码的精细测量，需要额外处理低层细节 |

书中把微秒以上的事件作为系统计时器的适用例子，把更短的事件作为 TSC 的用途；关键是**读两次表也花时间，计时开销不能淹没被测工作**。

书里给出过约 500 ns 和约 5 ns 的读取开销对比。这些数字只能当参考，不能当成所有机器的固定成本。Linux 的 `clock_gettime` 在支持时可以走 vDSO，不一定真的陷入内核。补充依据：[Linux 时钟接口文档](https://man7.org/linux/man-pages/man3/clock_gettime.3.html)。

下面是普通 C++ 耗时测量的骨架，`work()` 代表要测的实际工作：

```cpp
using Clock = std::chrono::steady_clock;

auto start = Clock::now();
work();
auto stop = Clock::now();

auto elapsed = std::chrono::duration<double, std::milli>(stop - start);
std::cout << elapsed.count() << " ms\n";
```

这个骨架需要 `<chrono>`、`<iostream>`，也需要保证 `work()` 的实际计算没有被编译器删掉，见下一节。

### 三个容易误会的地方

1. **返回纳秒，不等于能准确测出 1 ns 的差别。** 显示单位、时钟分辨率、读取开销和测量准确度是不同的事。
2. **TSC tick 不等于 CPU 实际执行周期。** 原书这里讨论的是恒定速率的参考计数；CPU 睿频后，同样一段时间内实际核心周期数可以增加，但 TSC 不会跟着同比例加速。
3. **两次裸 `__rdtsc()` 相减，不是一套完整的严谨微基准。** 还要考虑执行顺序、计时开销等；`RDTSC` 本身不是串行化指令。实际使用应采用验证过的测量方法。补充依据：[Intel 指令手册 RDTSC 条目](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-2b-manual.pdf)。

## 6. 微基准：先确认你要测的代码真的执行了（§2.6）

**微基准（microbenchmark）**就是把一个小功能单独拿出来测，例如比较两种字符串处理方式。它很适合快速验证猜想，但有两个大坑。

### 坑一：你以为在测构造字符串，其实循环可能被删了

书中的例子大意是：

```cpp
for (int i = 0; i < 1000; ++i) {
    std::string s("hi");
}
```

`s` 没有被使用，优化编译器可能发现这些工作对程序可观察的结果没影响，于是把整段循环消掉。测出来飞快，可能只是因为**根本没干你想测的活**。

可以借助 Google Benchmark 这类框架及其 `benchmark::DoNotOptimize(s)`。但它也不是“禁止一切优化”的开关：常量折叠等仍可能发生，最终仍要看生成的代码或性能热点，确认目标工作存在。补充依据：[Google Benchmark 防优化说明](https://google.github.io/benchmark/user_guide.html#preventing-optimization)。查看机器码可参考 [[命令行工具/objdump]]。

### 坑二：小实验赢了，真实程序未必赢

反复处理同一小份数据，可能一直命中缓存；换成真实的大数据和资源争用环境，排序可能反过来。输入规模、数据分布、冷热状态都要尽量有代表性。

所以微基准回答的是：**“这个小功能在这些条件下，哪个实现更快？”** 要说整个应用更快，还得回到真实应用确认。

同样，单元测试输出的耗时不能直接代替 benchmark：它主要验证功能，输入和环境未必代表真实使用。

## 7. 最值得带走的方法：看到变快，再往下问一层（§2.7）

书里举了一个很有代表性的例子：给 C++ 类加 `final`，有人报告“整体快了 5%，部分测试快了 30%”。进一步检查才发现，大收益是异常点，两台测试机的内存配置也不同；统一环境后差异只剩 1% 以内，生成的机器码等证据也不支持原先的大幅收益。

**主动基准测试（active benchmarking）**就是主动追查结果的原因。可以依次问：

1. **做的活一样吗？** 输出是否正确，有没有漏算？
2. **环境一样吗？** 机器、输入、编译参数、负载和缓存状态是否可比？
3. **结果稳定吗？** 整组结果如何，有没有只挑最快的一次？
4. **快在哪里？** 热点函数、执行指令数、缓存未命中、缺页或上下文切换是否发生变化？
5. **能解释吗？** 例如少做了拷贝、减少了分配、改善了数据局部性；证据是否支持这个解释？

不必每次都把所有指标采一遍。围绕当前假设，往下找能验证它的证据。这和 [[其他/Debug 复盘：从寻找答案，到系统性消除不确定性]] 的思路很接近。

## 下次测性能，可以直接照这个顺序做

1. **定问题**：要改善总耗时、吞吐，还是慢请求？先选指标。
2. **定工作负载**：用有代表性的输入，明确冷启动还是稳定运行。
3. **留基线**：保存旧版本和测试配置，确认前后完成相同工作。
4. **公平地多测几次**：先看波动；波动大就排查原因。
5. **看分布并算收益**：按目标看平均值、中位数或尾延迟，说清口径。
6. **往下验证原因**：检查热点和相关指标，再回真实应用确认。

把这个流程用在 LLM serving 上，也是先固定模型、输入输出长度和并发等条件，再比较吞吐与延迟。具体操作见 [[MLSys/压测工具/AIPerf：压测 LLM Serving 与多轮数据集]]。

## Q&A：关机后，高精度计时器怎么“保持增长”？

> [!note] 保留原来的阅读问答
> **单调时钟不承诺跨关机、重启连续计时。电脑关机后日期还能接着走，靠的是另一套接力机制。**

- **单调时钟**关心“经过多久”，适合算耗时。Linux `CLOCK_MONOTONIC` 以本次启动为参照，不计系统挂起的时间，也不保证跨重启连续。
- **墙上时间**关心“现在几月几号几点”。常见 PC 由电池供电的 RTC 在关机时继续走；启动后操作系统用它初始化时间，联网后再通过 NTP 等方式校准。

```text
关机期间：RTC 继续走时
    ↓
开机：OS 读取 RTC，建立日期时间基准
    ↓
运行中：硬件计数器累计时间偏移，配合校时维护系统时间
```

因此，不能把书里“从 epoch 开始计数”和“单调”直接拼成“一个从 1970 年开始、关机后也一直递增的 CPU 计数器”。测耗时优先用单调时钟；记录日期用日历时钟。

还有两点补充，避免把原来的解释读得过于绝对：

- `CLOCK_MONOTONIC` 不会因修改日历时间而突然跳变，但可受 NTP 渐进调速影响；`CLOCK_MONOTONIC_RAW` 不接受这类调速。见 [Linux 时钟接口文档](https://man7.org/linux/man-pages/man3/clock_gettime.3.html)。
- 在选择 TSC 作为 clocksource 的 Linux 系统上，系统计时接口与直接读取 TSC 可以建立在同一个硬件计数器上。前者提供换算好的标准时间，后者读原始 tick；但不能据此假定所有机器都用 TSC，或所有核之间永远同步。RTC、跨核同步及 TSC 稳定性的背景见 [Linux 内核计时文档](https://www.kernel.org/doc/html/latest/virt/kvm/x86/timekeeping.html)。

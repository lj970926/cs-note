# 通信时间的组成与 α-β 模型

## 经典网络：传输时间 = 传输时延 + 传播时延

一次数据传输的总时间由两部分构成：

- **传输时延（Transmission Delay，也叫发送时延）**：把数据"推到"链路上花的时间，等于 **数据量 ÷ 带宽**。与距离无关，由带宽决定。
- **传播时延（Propagation Delay）**：信号在介质中传播花的时间，取决于物理距离和介质中的传播速度（光纤中约 2/3 光速）。与带宽无关，是平时说的 latency 的主要部分。

经典类比：带宽大只是把"收费站发卡"变快（传输时延小），车在高速上跑的时间（传播时延）不变。

完整模型还要加上**排队时延**和**处理时延**，但前两者是主导项。

## 集合通信的 α-β 模型

NCCL / MPI 等集合通信领域用 **α-β 模型（latency-bandwidth model）** 表达同样的二分：

$$T(n) = \alpha + n \cdot \beta$$

- **α（启动时延 / latency term）**：与消息大小无关的固定开销——软件栈、kernel launch、每跳（hop）转发、链路传播。DeepEP benchmark 里报的 µs 级 latency 就是它。
- **β（每字节传输时间）**：**β = 1 / 带宽**，数据量 n 越大越主导。

**临界消息大小 n\* = α / β** 划分两个区间：n < n\* 时 latency-bound，n > n\* 时 bandwidth-bound。例如 InfiniBand NDR（α ≈ 2 µs，带宽 50 GB/s）的 n\* ≈ 100 KB。

> [!warning] NCCL 的现实差距
> 小消息下 NCCL 的协议开销（内存注册、channel 建立、kernel launch）会把**有效 α 放大 5–10 倍**于链路层时延；大消息下模型误差在 8–15% 以内。Ring/Tree 的实际切换点也会因此偏移，应以实测拟合为准。

各原语的 α-β 复杂度（p 个 rank、消息大小 n）：

| 原语 | 复杂度 |
| --- | --- |
| Ring AllReduce | $(2p-1)\alpha + 2\frac{p-1}{p} n\beta$ |
| AllGather / ReduceScatter | $(p-1)\alpha + \frac{p-1}{p} n\beta$ |
| All-to-All | $(p-1)\alpha + \frac{p-1}{p} n\beta$ |

## NCCL 里的相关术语

- **algbw（algorithmic bandwidth）**：数据量 ÷ 实际耗时，理想值。
- **busbw（bus bandwidth）**：algbw × 算法系数，反映链路真实跑出的带宽，**调优主要看这个**（nccl-tests 输出）。
- **Ring vs Tree**：Ring 大消息带宽最优（busbw ≈ (N−1)/N × 链路带宽），Tree 小消息时延更低；可用 `NCCL_ALGO` / `NCCL_PROTO` 强制指定做对比测试。
- **协议分档**：小消息走 LL / LL128，大消息走 Simple，按消息大小自动切换。

## DeepEP / MoE 场景下的意义

α-β 二分直接解释了 DeepEP 的两类 kernel 设计：

- **MoE decode 阶段消息小（每个 rank 几十个 token），由 α 主导** → low-latency kernel 用纯 RDMA + [[IBGDA]]（GPU 直接发起 RDMA，不过 CPU），把 α 压到 µs 级；带宽根本用不满，优化带宽没意义。
- **训练 / prefill 阶段消息大，由 β 主导** → normal（高吞吐）kernel 走 NVLink + RDMA 混合，追求带宽利用率。变长协商见 [[DeepEP normal dispatch 各 rank 不同 token 数]]。
- **对抗 α 的通用手段是通信-计算重叠**：`low_latency_dispatch(..., return_recv_hook=True)` 只发不收，先算 GEMM，再调 hook 收数据——把固定时延藏在计算后面，且不占 SM 资源。vLLM 中的落地见 [[vLLM DP 协调、CUDA Graph 与 DeepEP Low Latency]]。

一句话：**小消息优化 α（降低固定开销或 overlap 藏掉），大消息优化 β（带宽利用率），先判断自己在临界点的哪一侧。**

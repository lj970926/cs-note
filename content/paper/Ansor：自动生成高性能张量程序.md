# Ansor：自动生成高性能张量程序

论文：**Ansor: Generating High-Performance Tensor Programs for Deep Learning**，Lianmin Zheng 等，OSDI 2020，论文集 pp. 863–879。

[USENIX 论文主页（含原文、slides 和报告视频）](https://www.usenix.org/conference/osdi20/presentation/zheng)。本笔记以用户提供的 `Ansor.pdf` 为准；该 PDF 多一页会议封面，因此 **PDF 第 2 页 = 论文印刷页 863**。下文同时标出两种页码，图号沿用原文。

> [!abstract] 先记住这几个结论
> - **问题**：给出算子的数学定义，怎样自动得到适合目标硬件的高性能实现，并减少手写调优模板？
> - **第一层：搜索什么**。用通用推导规则生成程序骨架 **sketch**，再补齐 tile 大小、并行化、向量化、展开等 **annotation**，扩大可探索的实现范围。
> - **第二层：怎么找**。对完整候选程序做进化搜索，用学习型代价模型快速筛选，再用少量硬件实测纠正模型。
> - **第三层：先优化谁**。根据预计的端到端收益，把调优预算分给更值得优化的子图。
> - **结果**：在论文测试中，相对各平台的最佳其他方案，整网最高提升为 Intel CPU **3.8×**、ARM CPU **2.6×**、NVIDIA GPU **1.7×**。这些是最高值，并非平均加速比。
> - **边界**：这是 2020 年、静态 shape、稠密算子、FP32 的结果；不能直接当作现代 Tensor Core、低精度或动态 LLM serving 的性能结论。

## 1. 它到底在自动化什么？

### 1.1 数学定义和高性能实现是两件事

以矩阵乘法为例：

$$
C_{i,j}=\sum_{k=0}^{K-1} A_{i,k}B_{k,j}.
$$

这只规定“结果是什么”，没有规定：

- 循环按什么顺序执行、切成几层 tile，每层 tile 多大；
- 哪些工作分给 CPU 线程、GPU block 和 thread；
- 哪些数据放进中间 buffer、shared memory 或寄存器；
- 哪些循环向量化或展开；
- 若后接 bias、ReLU，在哪一层计算和融合它们。

这些决定了数据复用、访存局部性、并行度和资源占用。同一个数学式可以产生性能相差很大的实现。背景可联系 [[MLSys/算子/CUDA Tiling|CUDA Tiling]]：tile 越大不一定越好，需要在复用、资源容量与并发之间取舍。

这里的 **schedule** 指计算的执行组织方式；后文的 **task scheduler** 指“搜索预算分给哪个子图”。两者都叫调度，但职责不同。

### 1.2 过去两条路线各有什么问题？

![[IMG-20261028192613256.png]]

*原图 2：三种搜索策略。§2，印刷页 865 / PDF 第 4 页。*

| 路线 | 做法 | 论文指出的瓶颈 |
| --- | --- | --- |
| 模板引导搜索，如 AutoTVM | 专家先写好实现结构和可调参数，再搜索参数值 | 写模板需要算子与硬件知识；结构没写进模板，就搜不到 |
| 顺序构造搜索，如本文比较的 Halide auto-scheduler | 逐步决定程序如何构造，每步用模型保留少量候选 | 早期候选尚未完成，性能难预测，可能过早剪掉后续很好的程序 |
| Ansor | 自动推导多个结构，补成完整程序后再搜索、评价 | 需要同时解决空间覆盖、搜索效率和多子图预算分配 |

图 2 从左到右看：左边的橙色问号只能在固定骨架里填参数；中间每一步都会剪枝；右边先准备多种骨架，再补成完整程序并优化。

**为什么“不完整程序”特别难估？** 一个当前看起来差的实现，后面可能通过缓存、融合或 reduction 拆分变好；而标签来自能编译、能运行的完整程序。把在完整程序上训练的模型直接用于中途状态，会产生分布和信息完整度的问题。

![[IMG-20261028192613352.png]]

*原图 3：程序完整程度与模型排序质量。§2，印刷页 865 / PDF 第 4 页。*

横轴越靠右，程序越完整；左图是两两排序准确率，右图是 top-k 召回率。作者先用 20,000 个随机完整程序训练模型，再只应用一部分变换来构造不完整程序。信息很少时，左图接近随机排序的 50%，右图几乎找不回真正好的候选；完整程度提高后才明显改善。

这支持作者对该搜索设计的批评，**不等于证明任何面向部分程序专门设计的模型都不可能有效**。

## 2. 系统总览：三个层次形成反馈闭环

![[IMG-20261028192613390.png]]

*原图 4：Ansor 系统架构。§3，印刷页 866 / PDF 第 5 页。*

顺着图从上往下读：

1. **模型 → 子图**：先通过 Relay 的算子融合与图划分，得到多个较小的计算子图。
2. **Task Scheduler**：决定下一轮给哪个子图分配搜索资源。
3. **Program Sampler**：为这个子图生成 sketch，随机填 annotation，得到完整候选。
4. **Performance Tuner**：用进化搜索和代价模型找出值得实测的候选。
5. **Measurer**：编译并在目标硬件上测运行时间，把结果送回上面各层。

绿色回路很关键：**模型分数决定“值得测谁”，硬件实测决定“实际上谁快”，同时更新之后的搜索判断。**

为什么不直接把整张网络搜成一个超大程序？组合空间会爆炸。Ansor 在已有图划分的基础上优化子图，再协调子图之间的预算；它没有联合搜索所有整网划分、融合和底层实现。

输入也不是任意 Python 程序：核心输入是可分析的张量计算定义、shape 和目标平台。Ansor 使用自己的 IR 表示搜索状态，随后降低到 TVM IR，由后端完成代码生成。论文中的 Ansor 已集成进 Apache TVM，但它与当时的 **AutoTVM 模板搜索**是不同方案。

## 3. Program Sampler：先选结构，再填细节

### 3.1 为什么分成 sketch 和 annotation？

| 层次 | 决定什么 | 例子 |
| --- | --- | --- |
| Sketch，程序骨架 | 大体循环层级、融合关系、中间阶段与 reduction 组织 | 多级 tiling；matmul 与 ReLU 融合；引入 cache stage；使用 rfactor |
| Annotation，具体细节 | 让骨架成为可执行候选的具体选择 | tile 大小；parallel/vectorize/unroll；部分计算位置 |

这样可以把海量细节选择归到少量结构之下。作者报告典型子图的 sketch 数通常少于 10 个，但每个 sketch 可以对应极多具体实现。

**它仍然依赖人工编写的通用优化规则。** “不用手写模板”的含义是无需为每个算子和目标逐个写固定模板，并非系统凭数学式就能发明任意算法或优化。

### 3.2 Sketch 是怎么推出来的？

![[IMG-20261028192613455.png]]

*原表 1：CPU sketch 推导规则。§4.1，印刷页 867 / PDF 第 6 页。*

系统维护状态 $(S,i)$：$S$ 是当前部分构造的程序，$i$ 是正在处理的 DAG 节点。从输出侧开始向输入侧处理；若一条规则适用，就派生出后继状态。**同一状态可匹配多条规则，每种合法分支都可以继续展开**，最终收集各个骨架。

| 规则 | 作用 | 性能上的直觉 |
| --- | --- | --- |
| Skip | 这一条分支上跳过当前节点 | 保留另一种组织方式，避免强迫每个节点都套同一种优化 |
| Always Inline | 内联适合直接展开的简单逐元素节点 | 减少独立阶段和中间结果 |
| Multi-level Tiling | 给有数据复用的节点建立多级分块结构 | 匹配存储层次，增加复用 |
| Tiling with Fusion | 分块并把可融合的 consumer 接进来 | 在合适的 tile 内消费中间结果 |
| Add Cache Stage | 插入缓存输出阶段，之后可进一步融合 | 把局部累积与最终写回分开 |
| Reduction Factorization | 通过 rfactor 拆出部分归约阶段 | 在输出元素太少时，利用归约维度的并行性 |

适用条件来自读写模式等静态分析，比如节点是否存在数据复用、是否有合适的唯一 consumer、输出维度并行性是否不足。表里的 “Always Inline” 受其谓词约束，不能理解为任意逐元素算子都无条件内联最优。

### 3.3 看懂 `SSRSRS`，就看懂了一个重要骨架

CPU 的基础多级 tiling 结构是 **`SSRSRS`**：

- `S`：space loop，一组输出空间循环；matmul 里对应 $i,j$。
- `R`：reduction loop，一组归约循环；matmul 里对应 $k$。

因此它展开成：

```text
S        S        R     S        R     S
(i0,j0) (i1,j1)  k0   (i2,j2)  k1   (i3,j3)
```

原来三层的 $(i,j,k)$ 变成十层循环。骨架先规定层次，具体拆分因子之后再选。对于原始循环长度，有：

$$
I=\prod_{a=0}^{3} I_a,\qquad
J=\prod_{a=0}^{3} J_a,\qquad
K=K_0K_1.
$$

有些因子可以是 1，对应循环会被简化掉，因此这一个较深的骨架也能表达一些较浅的结构和不同的有效循环顺序。但它仍是受规则限制的搜索空间，不是所有合法循环程序的全集。

### 3.4 Rfactor 为什么能带来大收益？

如果输出只有很少几个元素，而每个元素需要很长的归约，单纯按输出划分任务，就没有足够多的并行工作。例如论文用 $2\times512$ 乘 $512\times2$ 说明这种情况。

Rfactor 的思路是先算多份部分和，再合并。下面是帮助理解的通用表达，**不是原图的逐行转写**：

$$
P_{i,j,q}=\sum_r A_{i,qR+r}B_{qR+r,j},\qquad
C_{i,j}=\sum_q P_{i,j,q}.
$$

原本只有 $(i,j)$ 可分配，现在部分和阶段还能利用 $q$ 的并行性，代价是增加中间结果和归约阶段。是否划算仍由搜索和实测判断；浮点加法重排也不应被理解为保证逐位相同。

### 3.5 从骨架到完整程序：图 5 是最值得细看的例子

![[IMG-20261028192613532.png]]

*原图 5：两个输入、三个 sketch、四个采样程序。§4，印刷页 869 / PDF 第 8 页。可放大查看代码。*

读图时沿着“左：数学定义和 DAG → 中：骨架 → 右：具体程序”移动：

- **第一组输入：matmul → ReLU**。Sketch 1 把 matmul 多级分块，并在 tile 范围内接上 ReLU。右边两个程序都来自这一骨架，但具体循环、并行与向量化安排不同；其中一个把 ReLU 留在独立的外部遍历中。
- **第二组输入：ReLU → padding → matmul**。Sketch 2 增加 `E.cache` 做局部累积，Sketch 3 改用 `E.rf` 组织部分归约。这体现了骨架层面的差异，已经超出“固定循环只改 tile 大小”。
- 最右列的循环可能少于中间列，因为填入 1 的循环层被消去了。

随机 annotation 会选择合法 tile 大小、部分外层循环并行化、内层向量化/展开，并微调部分节点的计算位置。论文这里的随机选择针对各步骤的合法值，采用均匀分布。**分层随机采样不能直接理解为整个程序集合上每个程序的概率都严格相同，更不能保证有限预算内覆盖全部程序。**

还有一个容易漏掉的优化：**按分块结构重写常量张量的布局**。推理里的权重可以提前重排，避免运行时再做一次转换。这个优化影响实验成绩；它也有“权重是编译时常量”的前提，不适用于任意动态输入。

### 3.6 GPU 与 CPU 有哪些不同？

§4.3 将基础结构从 `SSRSRS` 改为 **`SSSRRSRS`**，前三个空间层分别映射到 `blockIdx`、virtual thread 和 `threadIdx`；virtual thread 是编译调度概念，并非另一层物理 CUDA 线程。

还增加 shared memory 缓存节点和跨线程归约规则。可迁移的是“推导骨架—补齐细节—搜索—实测”的方法，**硬件映射规则仍需要针对平台设计**。

## 4. Performance Tuner：用模型找候选，用实测校正

### 4.1 为什么随机采样之后还要进化？

随机采样用于提供多样性，好的配置可能极稀少，靠随机撞到最优点效率低。Ansor 将新采样程序与之前表现好的程序一起作为初始种群，再通过变异和交叉改进。

下面是按 §3、§5 整理的概念伪代码，省略工程参数和具体候选维护细节：

```python
while tuning_budget_remains:
    task = scheduler.choose_task()
    population = sample_complete_programs(task) + reuse_good_programs(task)

    for generation in range(num_generations):
        scores = cost_model.predict(population)
        parents = select_with_fitness_bias(population, scores)
        population = mutate_and_crossover(parents)

    candidates = promising_programs_found_during_search()
    measurements = compile_and_measure(candidates, target_hardware)
    update_best_programs(measurements)
    measurement_history.extend(measurements)
    cost_model = retrain(measurement_history)
    scheduler.update(measurements)
```

这里有两个不同成本层级：**模型可以在秒级比较大量程序，而真正编译、执行只用于少量有希望的候选。** 模型预测的吞吐不是测量结果，也不保证排出的第一名真的最快。

### 4.2 进化操作具体改什么？

| 操作 | 怎么改 |
| --- | --- |
| Tile size mutation | 在同一轴的不同 tile 层之间移动因子，保持分块因子乘积不变 |
| Parallel mutation | 调整并行循环的粒度，例如融合相邻循环层，或进一步拆分 |
| Pragma mutation | 修改合法的编译提示，例如自动展开的最大步数 |
| Computation location mutation | 调整某些非多级分块节点的合法计算附着位置，例如 padding |
| Node-based crossover | 按 DAG 节点合并父程序的变换步骤，并处理依赖 |

最后一种需要解释：Ansor 保留“朴素程序如何一步步变成当前程序”的完整变换历史，把这些步骤当作基因。任意拼接会破坏依赖，所以交叉以节点为单位，再做依赖分析、调整和合法性检查。它没有对任意源码字符串做无约束拼接。

这样，搜索可以回头改之前的选择，不必一直沿着固定构造顺序向前走。**完整程序用于性能评价**，也不意味着 sketch 构造过程中不存在不完整中间状态；关键是没有用这些中间状态的预测性能过早淘汰整条路线。

### 4.3 代价模型学的到底是什么？

§5.2 使用 **梯度提升决策树（GBDT）**。特征来自完整程序中的算术与访存行为；对每个最内层非循环语句提取特征并预测分数，再把语句分数相加得到整个程序的预测分数。

设 $S(P)$ 是程序 $P$ 的最内层非循环语句集合，$f_\theta(s)$ 是模型对语句 $s$ 的输出，则：

$$
\hat y(P)=\sum_{s\in S(P)} f_\theta(s),
\qquad
\mathcal L(P)=y(P)\left(\hat y(P)-y(P)\right)^2.
$$

$y(P)$ 是同一 DAG 内归一化到 $[0,1]$ 的实测吞吐。**直接用 $y$ 作损失权重，让较快的程序更受关注**，因为搜索真正需要识别的是优秀候选。

需要区分三件事：

1. 它用分解后的语句特征预测完整程序分数，不是在运行时逐条语句计时后相加。
2. 一个模型可以共同学习不同 DAG 的程序；标签先在各自 DAG 内归一化。
3. 可复用的是模型设计与特征形式。换硬件后仍需要相应测量数据，论文没有证明无数据即可迁移性能判断。

作者表示整网调优的测量样本通常少于 30,000 个，树模型在这个规模上训练很快，因此每次用累计数据重新训练，而非必须做增量更新。

## 5. Task Scheduler：把预算花在最有收益的地方

### 5.1 为什么每个子图测 1,000 次不够聪明？

假设某子图只占整网 1% 的时间，把它提速一倍，整网也只减少约 0.5% 的时间；另一个子图占 40%，小幅提速就可能更值得。另一方面，当前最慢的子图也可能已经很难再优化，继续搜索只会浪费预算。

因此需要综合考虑：**当前耗时 × 出现次数 × 继续投入预算可能获得的改进**。

一个 task 对应一个子图优化问题。相同子图可在网络内重复出现；不同 shape 的卷积通常要作为不同任务处理。论文以 ResNet-50 的 29 个不同子图任务为例。

### 5.2 优化目标怎么写？

令 $t_i$ 为任务 $i$ 已获分配的资源单位数，$g_i(\mathbf t)$ 为当前找到的该任务最小执行延迟。**一个资源单位是一轮候选生成与批量实测，不是固定一秒**；因此调度收益不应直接解释成严格的“每秒收益”。

单网端到端延迟近似为：

$$
F(\mathbf t)=\sum_{i=1}^{n}w_i\,g_i(\mathbf t),
$$

其中 $w_i$ 是该子图在网络中的出现次数。若暂时只关注任务自身投入的作用，链式法则可直观写成：

$$
\frac{\partial F}{\partial t_i}
\approx w_i\frac{\partial g_i}{\partial t_i}.
$$

这把“单个子图还能改进多少”转换成“整网能改进多少”。原论文写法允许任务之间的知识共享，所以并不要求 $g_i$ 只依赖 $t_i$。

### 5.3 不能真的求导，怎么办？

搜索表现是离散、带噪声、事先未知的。§6.2 对梯度做启发式估计，结合：

- **最近的实际进步**：回看一个窗口内增加预算后，最优延迟下降了多少；
- **对未来进步的乐观估计**：避免一时没有进步就永远放弃某个任务；
- **相似任务的结果**：用相关任务已经达到的计算吞吐估计当前任务的潜力。

流程是先给每个任务一轮 round-robin 预热，再优先分配给估计目标梯度绝对值最大的任务；同时保留 $\varepsilon$ 概率随机探索，直到预算用完。

> [!example] 一个只用于理解的例子
> A 子图出现 8 次，下一轮预计每次少 0.05 ms，整网约节省 0.4 ms；B 出现 1 次，预计少 0.2 ms，则 A 更值得先调。若 A 已连续多轮不再变快，调度器会降低它的优先级。这组数字不是论文实验数据。

这里的 gradient descent 是**调优资源分配的离散近似策略**，不是对 tile 大小或机器代码做连续梯度下降。

### 5.4 还能优化哪些目标？

原表 2 还列出多网目标：所有模型延迟之和；达到延迟门槛后减少继续投入；最大化相对基线加速比的几何平均；结合历史表现进行单任务早停。其共同点是先明确系统级目标，再决定底层搜索该往哪里花资源。

## 6. 实验：哪些结论是证据支持的？

### 6.1 先看实验条件

| 项目 | 本文设置 |
| --- | --- |
| 时间背景 | 2020 年的软件与硬件生态 |
| 数值类型 | 所有评估使用 float32 |
| 硬件 | Intel 服务器 CPU、NVIDIA V100、树莓派 3B+ 的四核 Cortex-A53 |
| 单算子 | 10 类算子 × 4 个 shape × batch 1/16，共 80 个测试；在 Intel CPU 上测 |
| 子图 | ConvLayer：conv2d + BN + ReLU；TBS：两个 transpose + batch matmul + softmax；CPU/GPU |
| 整网 | ResNet-50、MobileNet-V2、3D-ResNet-18、DCGAN、BERT |
| 搜索预算 | 单算子/子图每个测试最多 1,000 次实测；整网最多 $1,000\times n$ 次，$n$ 是子图任务数 |
| 指令集设置 | 单算子和子图比较禁用 AVX-512，因为 Halide 的预训练模型不支持；整网 CPU 比较为所有框架启用 AVX-512 |

> [!note] 原文的硬件标注有一处不一致
> §7 正文写的是 **18 核 Xeon Platinum 8124M @ 3.0 GHz**，但图 6、图 8 的图注写 **20 核 Xeon Platinum 8269CY**。本笔记保留这个矛盾，不擅自认定哪一个才是实际平台。涉及精确复现时需要进一步核实。

主要基线包括 PyTorch 1.5、TensorFlow 2.0、AutoTVM，以及单算子/子图里的 Halide auto-scheduler、FlexTensor；GPU 整网还比较 TensorRT 6.0，ARM 比较 TFLite 2.0。它们并不是每张图里都齐全：论文当时 Halide 的 GPU 支持仍在实验阶段，部分框架不支持某些子图或模型。

**图 6、8、9 的纵轴是归一化吞吐，不是原始毫秒。** 图 6、8 还会对多个 shape 的结果做汇总；误差棒反映 shape 间的归一化表现差异，不能统一当作多次测量噪声或置信区间。柱子为 1 表示该组比较的最好表现，不表示不同模型的绝对速度相同。

### 6.2 单算子：更大的有效空间确实找到了不同实现

![[IMG-20261028192613768.png]]

*原图 6：单算子结果。§7.1，印刷页 873 / PDF 第 12 页。*

作者报告相对其他搜索框架的提升为 **1.1–22.5×**。大幅提升并不只来自搜索器“更会猜参数”，还来自空间里有其他方案缺少的优化：

- **NRM，矩阵 2-norm**：Ansor 可以利用归约循环并行性。
- **T2D，转置卷积**：合适的分块与展开，使代码生成器可以简化含零元素的乘法，减少无用工作。
- 一些基线无法覆盖足够多的 tile 层次、padding 计算位置或融合方式。

### 6.3 子图：融合能力也是优势来源

![[IMG-20261028192613876.png]]

*原图 8：ConvLayer 和 TBS 子图。§7.2，印刷页 873 / PDF 第 12 页。`@C` 是 CPU，`@G` 是 GPU。*

报告的优势范围为 **1.1–14.2×**，比较对象包括手工库与其他搜索框架。FlexTensor 在部分单算子上不错，但缺少跨算子融合支持，在子图里优势下降；它还无法运行较复杂的 TBS。

因此这些柱状图比较的是各方案能生成和执行的整个子图实现，不能把所有提升都归因于单个 GEMM kernel 更快。TBS 也只是注意力中的一个模式，不等于完整 Transformer 层。

### 6.4 整网：最高 3.8×，但不是所有网络都一样快

![[IMG-20261028192613938.png]]

*原图 9：三类平台的整网推理结果。§7.3，印刷页 874 / PDF 第 13 页。*

正文区分了两种比较：

| 比较对象 | 论文报告的提升 |
| --- | --- |
| 相对 AutoTVM | 各测试中为 1.0–21.8× |
| 相对该平台/测试中的最佳其他方案 | Intel CPU 最高 3.8×；ARM CPU 最高 2.6×；NVIDIA GPU 最高 1.7× |

不能把“对 AutoTVM 的最大提升”换成“对最佳其他方案的最大提升”，也不能把 CPU 单算子的 22.5× 当作 GPU 整网结果。

DCGAN 的收益很突出，论文将其联系到转置卷积优化。另一方面，AutoTVM 在 Intel CPU 的 ResNet-50 上已有很强的模板和全局布局搜索。Ansor 没有做同样的全局 layout search，但会重写常量权重布局；作者报告这一重写在 Ansor 的 ResNet-50 上带来约 **40% 性能提升**。

这说明结论不是“模板一律不行”，而是**固定模板会限制覆盖范围，通用生成规则能在更多 shape 和算子上寻找合适实现**。

### 6.5 消融：空间、细调和预算分配各自做了什么？

![[IMG-20261028192613824.png]]

*原图 7：ResNet-50 中一个卷积、batch 16；曲线为五次运行的中位数。§7.1，印刷页 873 / PDF 第 12 页。横轴是实测次数。*

| 变体 | 改了什么 | 从图中可读出的结论 |
| --- | --- | --- |
| Limited space | 限制 tiling 层次、内层 tile 大小和计算位置，使空间接近手工模板 | 候选不在空间里，再多搜索也找不到 |
| No fine-tuning | 保留大空间，但只随机采样 | 空间大仍需要有效探索 |
| Beam search | 在构造时对不完整程序剪枝，且不做 fine-tuning | 这个实现的早期性能估计会错过好候选 |
| Ansor | 大空间 + 完整程序细调 | 此测试中最终性能与收敛表现最好 |

**图 7 的 Beam search 变体同时改变了剪枝方式并去掉 fine-tuning**，因此不宜把曲线差距全部当作“只改变评价完整程度”的纯单因素因果结果。

![[IMG-20261028192614041.png]]

*原图 10：单独调 MobileNet-V2，以及联合调 MobileNet-V2 + ResNet-50。§7.3，印刷页 874 / PDF 第 13 页。纵轴是相对 AutoTVM 的加速比。*

`No task scheduler` 用 round-robin 给子图分配相同数量的资源单位。与它相比，完整 Ansor 更快提升目标性能，最终也更好。尤其在多网共同调优时，任务数增加，预算分配的作用更加直接。

两张图连起来看：**更大的空间决定可能达到哪里；细调决定能否在预算内接近好位置；task scheduler 决定先在哪些子图上取得整网收益。** 这些消融支持组合设计，但没有分别量化每一种变异、每条推导规则的独立贡献。

### 6.6 搜索效率：省下的是调优成本

![[IMG-20261028192614170.png]]

*原表 3：在 Intel CPU、batch 1 上，Ansor 达到 AutoTVM 性能所需的实测次数和墙钟时间。§7.4，印刷页 875 / PDF 第 14 页。*

下表将墙钟时间换算成更容易比较的形式，原始值单位仍是秒：

| 网络 | AutoTVM 时间 | Ansor 时间 | 调优时间缩短倍数 |
| --- | --- | --- | --- |
| ResNet-50 | 39,250 s，约 10.9 h | 4,540 s，约 75.7 min | 8.6× |
| MobileNet-V2 | 58,468 s，约 16.2 h | 660 s，11 min | 88.6× |
| 3D-ResNet | 7,594 s，约 2.1 h | 2,296 s，约 38.3 min | 3.3× |
| DCGAN | 4,914 s，约 81.9 min | 420 s，7 min | 11.7× |
| BERT | 12,007 s，约 3.3 h | 266 s，约 4.4 min | 45.1× |

**这是“达到 AutoTVM 这一性能水平”所需的时间，不是 Ansor 搜到自己最终最好结果所需的总时间，更不是推理提速 88.6×。** 作者明确说，单机为一个 DNN 生成充分优化的程序，通常仍需数小时。

实测次数的减少来自空间、细调和任务调度；墙钟时间还受编译、测量实现等影响。例如 Ansor 在 CPU 上显式刷新部分 tensor 的 cache，以更少重复次数取得稳定测量。因此墙钟加速比不能全部归因于搜索算法本身。

### 6.7 模型预测得准吗？

![[IMG-20261028192614316.png]]

*原图 11：预测吞吐与实测吞吐。§7.5，印刷页 875 / PDF 第 14 页。*

数据来自 Intel CPU 上调 ResNet-50 时测得的 25,000 个程序，随机拆为 20,000 个训练样本和 5,000 个测试样本：

| 指标 | 结果 | 意义 |
| --- | --- | --- |
| RMSE | 0.079 | 归一化吞吐的预测误差 |
| $R^2$ | 0.958 | 拟合程度；不是 95.8% 的排序准确率 |
| Pairwise comparison accuracy | 0.851 | 两个程序谁快谁慢的比较准确率 |
| Recall@30 of top-30 | 0.624 | 预测最快的 30 个里，找回了多少实测最快的 30 个 |

左图点越靠近对角线越好；预测为负数是模型输出的分数，不是程序真的存在负吞吐。实测为零的点包含无效或超时程序。右图按预测从慢到快排序，实测总体随之上升，说明模型有筛选价值。

但 **top-30 召回只有约 62.4%**，所以不能只相信一次模型排序。还应注意样本是搜索过程中收集的，同一场景内随机划分；它没有证明对新硬件、新 DAG 或新算子分布也有同样精度。

## 7. 论文的边界与容易误读的地方

§9 的明确限制，以及由实验范围得到的阅读判断：

| 边界 | 应怎样理解 |
| --- | --- |
| 不支持动态 shape 图 | 分析、空间构造和测量需要事先知道 shape；原文没有解决通用动态 shape 调度 |
| 只支持稠密算子 | 稀疏计算的数据结构、访存和空间需要重新设计 |
| 特殊硬件指令利用不足 | 原文承认对 VNNI、Tensor Core、ARM Dot 等支持不充分；仍依赖 LLVM/NVCC 等后端 |
| 高层循环优化为主 | 不负责在任意机器指令集合里做完全自由的超级优化 |
| 图划分作为上游输入 | 子图内可以优化融合，但没有联合穷举整网划分和所有图改写 |
| 搜索空间由规则限定 | 能找到规则可表达的好实现，不保证发现新的数学算法，也不保证全局最优 |
| 离线搜索仍有成本 | 适合部署前付出调优成本、之后反复运行的场景；不是每次请求在线搜索 |

原文在 §4.1 说可注册新规则来扩展特殊算法或硬件支持，与 §9 的限制并不矛盾：**可扩展接口表示可以继续实现，不表示本文已经评估了这些能力。**

另外，原文的程序合法性依赖受限变换集合和依赖检查。这与“任意生成代码都已经被严格验证”“浮点结果保证逐位一致”是不同强度的结论。

## 8. 放到已有知识里，怎样记住 Ansor？

### 8.1 与 CUDA Tiling：从手工权衡变成可搜索的决定

[[MLSys/算子/CUDA Tiling|CUDA Tiling]] 解释分块为什么有用，Ansor 则回答：**不同算子、shape 和硬件上，谁来决定分块层次、参数和相邻计算的位置？** 它把这些决定编码成规则与搜索变量，再用硬件反馈筛选。

### 8.2 与 FlashAttention：结构化调度和算法创新的边界

[[paper/FlashAttention- Fast and Memory-Efficient Exact Attention with IO-Awareness|FlashAttention]] 不只有 tile 参数，还依赖 online softmax 等计算重组织。由此得到的阅读判断是：一个调优系统再擅长搜索，若输入表达和规则不能描述这种重组织，就不能指望仅靠扩大参数搜索自动发现它。这个比较用于理解能力边界，论文没有做两者的实验比较。

### 8.3 与 KernelAgent：共同的是实测闭环，候选来源不同

[[MLSys/KernelAgent：硬件反馈驱动的 GPU Kernel 优化|KernelAgent]] 的候选主要由 LLM 结合诊断与历史改写；Ansor 的候选来自显式循环变换、骨架和进化操作。两者都体现“提出候选—执行测量—保留有效结果—继续探索”，但 **Ansor 的 learned cost model 是预测吞吐的树模型，不是 LLM，也不是自动给出瓶颈解释的 Agent**。

本节是结合现有笔记的理解，不属于 Ansor 原论文声称的后续工作或实验结果。

## 9. 真正值得带走的判断方法

看到一个自动调优系统时，可以沿着 Ansor 的三层结构检查：

1. **空间**：它能表达哪些实现？最优方案是否可能根本不在空间内？
2. **评价**：排序来自分析模型、学习模型还是实测？评价对象是完整程序还是中间状态？
3. **预算**：有限的编译和测速机会，优先给了哪些候选、哪些子图？
4. **结果口径**：报告的是单算子、子图还是整网？推理耗时还是调优耗时？最高值还是平均值？

如果只能记一件事：**Ansor 的贡献是把“能搜索到更丰富的实现”“高效筛选完整候选”“按系统收益分配搜索资源”连成了一套机制。**
